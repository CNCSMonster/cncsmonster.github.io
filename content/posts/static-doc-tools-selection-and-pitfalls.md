为数百篇 Markdown 笔记搭建本地预览与静态发布体系时，通常会遇到两个烦心事：

1. **写笔记时老被打断**：本地服务热重载慢，新建或者重命名文件后界面不更新，经常要手动重启服务；
2. **搜索不可靠（容易漏搜）**：搜索引擎对分词或通配符处理有问题，明明写过的笔记却搜不出来，让人心里没底。

### 核心选型速查（TL;DR）

- **普通个人知识库，默认首选 VitePress**：数千篇以内搜索只要 1~3 毫秒，写完保存就能搜，不用额外装搜索插件，热重载极快；
- **什么情况下选另外两款？**
  - 如果文档里必须跑 React / Vue 等交互式 Demo，选 **Astro Starlight**；
  - 如果重度依赖双向链接和知识图谱（类似 Obsidian），选 **Quartz 4.0**。

## 一、三种本地搜索引擎的差别

搜索好不好用，根本上取决于工具内置了什么搜索引擎：

| 搜索引擎 | 怎么工作的 | 优点 | 缺点与适用场景 |
| :--- | :--- | :--- | :--- |
| **Lunr.js**<br>*(老工具标配，如 MkDocs)* | 浏览器端纯 JS 计算，打开网页先下载整个索引大文件 | 生态老、轻量 | 英文词干处理和即时搜索通配符容易冲突，经常搜不到结果；长文章不能精确定位到段落。 |
| **MiniSearch**<br>*(VitePress 默认)* | 纯 TypeScript 编写，原生支持前缀匹配和模糊搜索 | 仅 7KB，前缀匹配好用，响应极快 | 也是一次性下载整个索引，万篇以上超大库会占用较多首屏带宽。 |
| **Pagefind**<br>*(Starlight 标配)* | Rust 编写，打包时生成切片索引，**按需分块下载** | 线上首屏开销低，大知识库加载快 | 依赖最终打包产物，在本地边写边预览时，无法做到保存后实时自动重建索引。 |

> **一句话总结**：在现代电脑上，几千篇笔记用 MiniSearch 搜索只要 1~3 毫秒，速度完全感觉不到延迟，而且写笔记时保存就能搜；只有笔记膨胀到几万篇、线上首屏加载太慢时，才需要换成 Pagefind。

## 二、本地实时预览（热重载）的代际差异

| 对比维度 | **上一代工具（以 MkDocs 为例）** | **现代工具（以 VitePress / Starlight 为例）** |
| :--- | :--- | :--- |
| **底层实现** | Python 脚本 + 简单的文件监听 | **基于 Vite 的现代前端热重载** |
| **新建/重命名文件** | ❌ 只能感知修改已有文件。新建或者重命名文章时，目录树不会自动更新，必须修改已有文件才能触发重新构建。 | ✅ 新建、修改、重命名任何 `.md` 文件，页面和左侧目录树都会立即刷新。 |
| **本地与线上一致性** | ⚠️ 本地预览是动态渲染，打包产物是静态文件，偶尔出现“本地看着正常，打包上线就错乱”的问题。 | ✅ 本地开发与静态打包用同一套解析逻辑，本地什么样，打包出来就是什么样。 |

## 三、工具横向对比与最终选择

| 工具 | 底层技术 | 组件支持 | 适合谁用？ |
| :--- | :--- | :--- | :--- |
| **VitePress** | Vite + Vue 3 | 可以直接写 **Vue 组件** | 追求省心、秒级打开、不需要折腾配置的个人技术笔记库。 |
| **Astro Starlight** | Vite + Astro + Pagefind | 支持 **MDX**（可以混用 React、Vue 组件） | 需要写复杂交互 Demo 的技术文档、多语言开源项目文档。 |
| **Quartz 4.0** | 针对 Obsidian 定制 | 支持 Obsidian 语法 | 强依赖双链 `[[link]]`、悬浮卡片和关系图谱的数字花园。 |

### 为什么最终选 VitePress？

1. **搜索最省心**：开箱自带 MiniSearch，不用自己找插件、写配置胶水层，几千篇笔记内搜得快、搜得准；
2. **写作体验好**：基于 Vite 的热重载极快，新建和修改文件都不需要手动重启服务；
3. **维护成本低**：Vue 3 生态成熟稳定，基本不需要花精力修补升级引发的配置问题。

## 四、实操踩坑记录

在实际配置与迁移过程中，有几处容易绊倒人的细节问题：

### 1. 打包（build）时报全局对象错误

- **现象**：本地跑 `npm run dev` 正常，一旦执行 `npm run build` 打包就报错：`ReferenceError: window is not defined`。
- **原因**：打包是在 Node.js 环境里跑的，Node.js 里根本没有浏览器的 `window` 对象。如果引入的第三方插件在顶层直接访问了 `window`，打包就会崩溃。
- **解决**：把这类组件放进 `<ClientOnly>` 标签里，或者在 Vue 的 `onMounted()` 钩子函数里动态加载，确保代码只在用户的浏览器端运行。

<details>
<summary>补充：什么是客户端水合（Hydration）？</summary>

现代静态文档工具在打包时，会先由 Node.js 把 Markdown 渲染成纯静态的 HTML 网页。此时页面加载极快，但上面的按钮是“死”的（还没有绑定点击事件）。

等用户的浏览器下载完 JavaScript 代码后，Vue 或 React 会扫描这具 HTML 骨架，把点击事件和交互逻辑“挂”上去——这个**把一具静态 HTML 激活成可交互网页的过程**就叫“水合”（Hydration）。

因为 `onMounted()` 钩子只会在浏览器端激活时执行，打包阶段会自动跳过，所以把依赖 `window` 的代码放进去就能避开报错。
</details>

### 2. Markdown 里的模板变量与 Vue 语法冲突

- **现象**：笔记里如果记录了包含 `{{ variable }}` 的代码或文本（例如 Jinja、Ansible 配置），会被误当成 Vue 表达式解析，直接报错构建失败。
- **解决**：行内写用反引号包裹（`` `{{ variable }}` ``）；如果是多行代码块，在最外层加上 `::: v-pre` 标记，告诉编译器跳过这块代码的解析。

### 3. 列表前缺少空行导致排版错乱

- **现象**：在编辑器里明明是列表，渲染出来后却缩进全无，挤成了一整行普通文字。
- **原因**：部分解析器规定列表前面必须空一行，否则会把列表强行拼到上一段落里当成普通文字。
- **解决**：所有数字列表（`1.`）或小圆点列表（`-`）前后，都严格留一行空行。
